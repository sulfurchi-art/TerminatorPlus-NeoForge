## 0. 用户的原话

> "我就是想尽可能的在mc当中还原现实世界小范围武装冲突的模式……不是像武装突袭，战地那样，而是找到一个节目效果和真实之间的取舍，MC版没必要严谨，观感好就行，现在的载具战基本上都是贴脸，观赏性较为一般"

> "我想做的其实就是这种战争模拟器，而不是原版的机器人追杀等等，当然前面的东西可以保留，但也应该彻底重构，和原版插件彻底撇清关系
> 而且应该加入正儿八经的，方便编辑战场的东西，而不是全靠外置agent，当然也可以作为一个可选项，而且调试开发的时候能很大程度上节约时间
> 现在的很多东西就是处于毛坯状态，功能确实是有，但是不显式，每次都要调用复杂的指令，后续最好做成可视化，可批量的面板.
> 而且最终一个殊途同归的问题就是，如何优化在机器人极多的时候，服务端的表现."

## 1. 定位

**在 MC 里还原现实中的小规模武装冲突：战术看起来要像真的，数值不必真，观感第一。**

- 介于两类游戏之间：
  - ArmA：硬核模拟，节奏慢，一枪倒。
  - 战地：街机式乱战，到处都在打。
- 不再是"会 PvP 的追杀机器人"。原插件里的追人、搭路、重锤、珍珠这些 PvP 技能不再是核心，最多作为步兵的可选技能保留。

**观感原则（来自上一轮讨论）：**

| 方面 | 现实 | MC 里的取舍 |
|---|---|---|
| 交战距离 | 坦克 1～3 公里互射 | 坦克在 60～120 格外打，打一炮换个位置；贴脸只留给最后的决战 |
| 节奏 | 长时间对峙，偶尔爆发 | 一局 3～8 分钟：接近 → 远距接触与压制 → 侧翼机动 → 近距决战 → 残部撤退 |
| 杀伤 | 一发就可能报废 | 要多次命中才毁。受伤后冒烟、放烟雾、后撤。远距离射击有散布 |
| 弃车 | 下车找掩护 | 先放烟雾再往烟里撤，不是一下车就死 |
| 直升机 | 几公里外悬停发射 | 在 80～150 格外、离地 30～60 格开火，打完降高躲避 |
| 压制 | 交火以压制为主 | 被打的一方准头下降、找掩体；曳光弹和爆炸让观众看得到火线 |
| 兵种 | 步坦协同 | 步战车放下步兵，反坦克小组找侧面，炮兵和无人机压制，防空掩护 |
| 目标 | 有任务的战斗 | 打剧本：村庄攻防、车队伏击、据点突袭、桥梁争夺，而不是死斗 |

## 2. 现状（截至 4.22 源码）

- **代码：**
  - 106 个 Java 文件，约 2.3 万行。
  - 包名仍是原插件的 `net.nuggetmc.tplus`，模组 id 是 `terminatorplus`，许可证 EPL-2.0。
  - 原插件的遗留：
    - `LegacyAgent`（1683 行）
    - `/ai` 神经网络和强化训练（`api/agent/legacyagent/ai`，约 700 行）
    - 反射式命令框架
    - `Terminator` 接口体系
  - 卓越前线兼容：`compat/`，约 2700 行，包括载具驾驶、乘员编组、驾驶仪表和枪械。这一部分是这段时间验证得最充分的。
  - `SelfTest.java` 有 4128 行，场景全塞在一个文件里。
- **观感：** 打得太快、太近、太准，也没有撤退。
  - 坦克 5v5 打了 70 秒。
  - 带直升机的 20v20，红队 46 秒全灭。
  - 每局六到七成的死亡是爆头。
  - 4.19～4.21 是按"进攻不够积极"的反馈调的，现在调过头了。
- **易用性：** 功能都藏在指令后面，没有可视化，也不能批量操作。
  - 布置一局要靠外部脚本：Claude 的 `tplus-arena` skill，用数据包函数一次执行几百条命令。
- **性能：**
  - 50v50（98 个人机加 24 辆载具）开打后没出现 "Can't keep up"，但**没有 MSPT 数据**。
  - 每个人机都是完整的假玩家（`Bot extends ServerPlayer`）。
  - 要显示 YSM 模型，人机必须进玩家列表，而玩家列表上限是 100。

## 3. 重构：和原插件彻底撇清

**新身份：**
- 新的模组名、模组 id、包名、指令前缀（待定名）、配置目录。
- 原插件的名字和 `nuggetmc` 包名都不再出现。

**去掉：**
- `LegacyAgent`。
- `/ai` 神经网络和种群训练，`/botenv`。
- 反射式命令框架，以及原插件的事件和调度 API。
- 只为 PvP 追杀服务的逻辑。
- Mojang 皮肤拉取改成可选。

**保留，但重写进新架构：**
- 卓越前线兼容：枪械、载具驾驶与乘员、无人机、C4、诱饵、导弹防御（按 feedback-4.21 改小）。
- YSM 联动。
- 载具导航。4.19～4.21 的成果，包括倒车、让行、侧翼。
- 步兵的机动技能（珍珠、鞘翅、图腾），作为可选技能。

**许可证提醒（不是法律意见）：**
- 现在的代码是从 EPL-2.0 的原插件移植过来的。
- 想真正撇清，新代码必须重新编写，不能复制原插件的代码；复制过来的部分仍然受 EPL-2.0 约束。
- 建议 Codex 记录哪些文件是全新编写的。

**迁移方式（建议）：新项目并行，逐块搬迁，不在原地大改。**
- 新模组从零搭骨架。
- 已经验证过的能力（卓越前线兼容、载具驾驶），每次搬一块，带着它的自测场景一起搬。
- 新模组达到"能打一局剧本"之前，旧模组继续部署用于测试。

## 4. 新架构（分层）

1. **运行时核心**
   - 单位（士兵）、调度器，包括每刻的 AI 预算、分帧和远近分级。
   - 感知：空间索引、视线缓存。
   - 导航：寻路缓存、编队路径。
   - 动作层：移动、瞄准、开火、用物品、上下车。
2. **兼容层**
   - 卓越前线：枪、载具、无人机、C4、诱饵、能量和弹药。
   - YSM：模型。
   - 都用适配器隔离，卓越前线升级时只改这一层。
3. **战术 AI，三层指挥**
   - **阵营指挥官：** 剧本目标、增援、呼叫炮火和无人机。
   - **小队：** 队形、目标分配、推进与换位、何时撤退。
   - **个人：** 射击、掩体、压制反应、上下车。
4. **条令数据化**
   - 写成数据文件，不改代码就能调：兵种；每类武器和载具的交战距离；撤退和士气阈值；压制强度；命中散布。
5. **剧本系统**
   - 场地、阵营、编制、出生点和路径点、目标（占点、护送、防守）、规则（命数、血量倍率、时限）、阶段与触发器、计分。
6. **编辑器与界面**：见第 5 节。
7. **遥测**
   - 战局日志：规格见 feedback-4.21 的 P1-5。
   - 观感指标（第 7 节）。
   - 性能计数器。

## 5. 战场编辑器与可视化面板

**约束：** 默认纯服务端，客户端不装模组也能进服。所以第一阶段只用原版客户端本来就能显示的东西：
- 箱子式菜单界面；
- 可点击的聊天菜单；
- Boss 栏和记分板；
- 展示实体（text/block/item display），用来在场上做标记；
- 粒子效果。

第二阶段可以做一个**可选的**客户端扩展，提供俯视地图和拖拽布兵。

**剧本文件：**
- 一局战斗就是一个剧本文件（JSON），存在 `config/<新模组>/scenarios/`。
- 可以手改，可以在游戏里编辑，也可以让 agent 生成。agent 是可选项，不是必需品。

**游戏内编辑：**
- **战场编辑棒：** 右键方块，放置出生点、路径点、目标点、阵地范围。场上用展示实体显示名字和范围，一眼就能看出这局怎么布置。
- **面板（箱子界面）：**
  - 阵营 → 编制 → 单位，逐层浏览。
  - 选中一批，批量改等级、配装、血量、模型、所属小队。
  - 一键：生成本剧本、清场、开打、停火、重开。
- **模板：**
  - 兵种模板：角色、配装、等级、模型。
  - 编制模板：步兵班、坦克排、"M1A2 车组 + 座位分配"等。
  - 按模板一次生成 N 个小队。
- **批量：** 框选一个区域，对区域内的单位批量操作。

**调试可视化：**
- 选中一个单位，显示它的目标连线、当前行为和导航状态、交战距离圈。
- 全局性能面板：MSPT、单位数、AI 预算用量。

**给 agent 的可选接口：**
- 剧本文件，加一组稳定的、输出结构化结果的指令。
- 建议开启只允许本机访问的 RCON：只监听 127.0.0.1，设密码，不能通过 Radmin 暴露出去。用它替代现在"模拟键盘往控制台打字"的做法，更快也更稳。

## 6. 人机很多时的服务端性能

**先测量，再优化：**
- 装 spark 性能分析模组。
- 建固定的基准场景：100 和 200 个人机待命；50v50 交战；24 辆载具行驶。
- 记录 MSPT 的 p50 和 p95，以及各系统的耗时占比。
- **目标（建议，待用户定）：** 100 个人机交战时 p95 ≤ 40 ms；200 个人机可玩（≤ 50 ms）。

**方向（收益要靠测量确认）：**
1. **AI 分帧和远近分级：** 不是每个人机每一刻都要重新想一遍。远离玩家、没有交战的单位降低频率；每刻的 AI 总耗时设上限。
2. **小队级感知和决策：** 小队共享目标和视线结果，N 个人的决策变成大约 N/5 个小队的决策。
3. **空间索引：** 按阵营建网格，找最近的敌人不用再扫描全部单位。
4. **寻路：** 缓存，编队共用路径，设预算（4.21 已经有每车、每刻的节点上限）。可以考虑在方块快照上异步寻路。
5. **热点代码：** 去掉每刻都会执行的对象分配和 stream。现有 28 个文件用了 stream，要逐个看哪些在每刻都执行的路径上。
6. **区块和网络：**
   - 人机不应该各自持有"玩家级"的区块加载票，只给战场区域加载就够了。
   - 远处的单位降低同步频率。
   - YSM 要求人机进玩家列表，这会占名额（上限 100），需要找替代方案。
7. **最根本的一项（先做技术验证）：** 普通士兵能不能换成更轻量的实体，只在必要时才用假玩家，比如用卓越前线的枪和载具、需要 YSM 模型的时候？
   - 先验证卓越前线和 YSM 对"必须是玩家"的依赖到什么程度，再决定。
   - 这一项影响整个运行时核心，越早验证越好。

## 7. 观感指标（每局自动统计，用来判断方向对不对）

| 指标 | 现在 | 目标（建议） |
|---|---|---|
| 一局时长（20v20） | 约 1 分钟 | 3～8 分钟 |
| 第一个击杀出现时间 | 开打后 4～20 秒 | 20～60 秒（先有接近和接触阶段） |
| 平均击杀距离 / 20 格以内击杀占比 | 没有数据（死亡消息里没有距离） | 坦克的击杀大多发生在 60 格以外，近距离击杀少于三成 |
| 爆头率 | 60%～73% | 30%～40% |
| 受损后撤出战斗的载具 | 几乎没有 | 每局都有 |

这些指标靠遥测层的战局日志来算。新模组做出来之前，Claude 可以先在服务器上用 KubeJS 写一个临时的击杀距离记录器。

## 8. 路线图（建议）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M0 立即**（不等重构） | Codex：在旧模组上收回一部分"射程内主动推进"，处理 feedback-4.21。Claude：在服务器侧做剧本化场地（村庄、车队路线）和临时击杀距离记录 | 观感指标开始有数据 |
| **M1 新骨架** | 新身份和项目结构；运行时核心（调度、预算、分级）；迁移卓越前线兼容；基准场景 + spark 测量；技术验证：轻量士兵实体 | 100 个人机待命的 MSPT 达标，自测全部通过 |
| **M2 战术 AI** | 三层指挥；条令数据化（交战距离、撤退、压制、散布） | 观感指标达到第 7 节的目标 |
| **M3 剧本与编辑器** | 剧本文件、编辑棒、箱子面板、模板、批量操作、调试可视化（纯服务端） | 不用任何外部脚本，在游戏里就能搭一局并开打 |
| **M4 节目效果** | 战场播报、Boss 栏和侧边栏、战报；剧本库（村庄攻防、车队伏击、据点突袭、桥梁争夺） | 一局有明确的开场、高潮、结局 |
| **M5 性能冲刺** | 200 个人机；轻量士兵实体（如果技术验证可行） | 200 个人机可玩 |
| 可选 | 客户端扩展（俯视地图、拖拽布兵） | — |

**上表每个阶段的验收，都必须包含"用户在实战里看过标准对局并认可"。** 只有自测通过，不算完成。

## 9. 开发方法：以实测为准

> 用户原话："而且必须得大量时间反复测试才知道是不是shit，纯ai闷头乱实验乱冒烟做出来的肯定是shit"

1. **自测通过不等于好用。**
   - 例子：4.21 的 28 项定向自测全部通过，实战里却是全员贴脸，一分钟打完。
   - 自测只能证明"没坏"。好不好看，只能靠实战和人眼。
2. **人来判断，AI 来准备。**
   - AI（Codex、Claude）负责：提出改法、实现、搭好测试、跑数据。
   - "是不是 shit"由用户看过实战后判断。用户没看过的改动，不算完成。
3. **每一步都要能打一局。**
   - 重构也好，新功能也好，都不能长时间闷头憋大招。
   - 每个阶段都拆成小块，每一块在一次测试里就能看出效果。
4. **一次只改一类行为。** 一次改得越多，越分不清是哪一处让效果变好或变坏。
5. **固定的标准对局（回归场景）。**
   - 每个版本都跑同一组场景，例如：5v5 坦克、20v20 载具、步兵班对抗、直升机对防空。场地和阵容都保持一样。
   - 结果和上一版并排比较：一边看观感指标，一边听用户评价。
6. **把每次测试的成本降到最低。** 这正是编辑器和剧本系统的价值：
   - 一键布置、一键重开。
   - 开发期加"行为开关"：同一个版本里可以在新旧两种行为之间切换，一场测试里就能对比，不用来回换包重启。
   - 测试的人应该把时间花在看和判断上，而不是花在敲命令上。
7. **每次测试都留记录。**
   - 版本、场景、指标、用户原话，都写进观察记录。
   - 反馈文档引用原话，后来的人能追溯每个决定是怎么来的。

## 10. 需要用户决定

1. **新名字：** 模组名和指令前缀。是否新开一个仓库？
2. **迁移方式：** 新项目并行、逐块搬（建议），还是原地重构？
3. **界面：** 第一阶段是否坚持纯服务端，即客户端不装模组也能用全部编辑功能？
4. **性能目标：** 要支持多少个人机（100？200？），能接受的 MSPT 是多少？
5. **RCON：** 是否开启只允许本机访问的 RCON，给 agent 用？
6. **第一个剧本：** 村庄攻防还是车队伏击？
